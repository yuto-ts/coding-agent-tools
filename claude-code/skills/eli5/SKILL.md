# eli5

## 概要

対象トピック: $ARGUMENTS

そのトピックを初めて聞く人に向けた説明を、HTML アートファクトとして作る。文字で埋めるのではなく、図を主役にして文字を削る。読み終えたときに「何が、何をして、何が起きるのか」を絵で思い出せる状態を目標にする。

正確さは削らない。単純化してよいのは詳細の省略までで、事実と違うことは書かない。

## 手順

1. 説明する対象の中で、読者が最初に理解すべき1つの仕組みを決める。全体像を並べるのではなく、そこから始める。
2. 画面（セクション）を4〜7個に割る。1画面 = 1つの考え。
3. 画面ごとに下の「図の型」から1つ選ぶ。選べない画面は、その画面が図を必要としていないか、内容が2つに割れている。
4. `artifact-design` skill を読み込む。図を描く画面がある場合は `artifact-diagramming` skill も読み込む。
5. HTML を書き、Artifact ツールで公開してリンクを渡す。

## 図の型

画面ごとに、以下のどれかを選ぶ。

| 型 | 使いどころ | 中身 |
|---|---|---|
| 流れ図 | 手順、時間順、リクエストの経路 | 箱と矢印。分岐は2本まで。番号を振る |
| 断面図 | 箱の内部構造、外から見えない部品 | 外枠を薄く描き、中の部品に名前を付ける |
| 前後比較 | 変化、改善、2つの方式の違い | 左右または上下に並べ、違う箇所だけ色を変える |
| アナロジー図 | 抽象的な概念を身近な物に置き換える | 左に身近な物、右に対象、対応する部分を線で結ぶ |
| 分解図 | 構成要素が3つ以上あり、役割が違う | 部品を並べ、それぞれに1行の役割を添える |
| 量の比較 | 桁が違う数字、速度差、容量差 | 面積か長さで見せる。棒の横に実数を書く |

矢印には必ず動詞のラベルを付ける（「送る」「聞く」「返す」）。ラベルのない矢印は、読者にとって意味が確定しない。

## 1画面の分量

- 見出し: 日本語で12文字以内、英語で6語以内。
- 本文: 2文以内。1文は40文字（英語なら20語）を目安に切る。
- 図: 1つ。図の中の文字は6箇所以内。
- 箇条書きは使わない。並べたい項目があるなら図の中に置く。

この上限を超えたら、文を削るのではなく画面を割る。

## 比喩の作り方

- 読者が確実に知っている物にだけ置き換える（郵便、行列、鍵と錠、地図、レシピ）。
- 1つの説明に比喩は1系統だけ。途中で別の比喩に乗り換えない。
- 擬人化しない。「サーバが知りたがる」ではなく「サーバが問い合わせる」と書く。
- 比喩が成り立たなくなる点を、最後に1行で書く（「実際の DNS はこの郵便局と違い、答えを一定時間覚えておきます」）。

## 言語と用語

- 質問された言語で書く。日本語で聞かれたら日本語、英語で聞かれたら英語。
- 専門用語と固有名詞は原語のまま残す。DNS を「名前を調べる係」に改名しない。用語はそのまま出し、初出時に1行の言い換えを添える。
- 略語は初出時に展開する。

## 締めの画面

最後の画面には、以下を置く。

- この説明で省いたことのうち、次に知ると効くもの3項目まで。1項目1行。
- 比喩を使った場合は、その比喩が破綻する点。

「まとめ」として本文の再説明を書かない。すでに読んだ内容を3回言わない。

## HTML の作り方

- `artifact-design` skill の指示に従う。図は inline SVG で描き、外部リソースを読み込まない。
- ライトとダークの両方で読めるように、色は CSS 変数で定義する。
- 本文の文字は 20px 以上。図の中のラベルも小さくしない。
- 1画面は縦スクロールで区切る大きなセクションにする。横スクロールは作らない。
- 画面の切り替わりが目で分かるように、余白を大きく取る。

## コードの説明に使う場合

トピックがこのリポジトリのコードやアーキテクチャの場合は、まず対象のファイルを読んでから書く。推測で図を描かない。読んだファイルは、締めの画面にパスで列挙する。
