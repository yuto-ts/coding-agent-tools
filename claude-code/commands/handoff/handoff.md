# 目的

このセッションの会話・調査結果・決定事項を、**別セッションの Claude がゼロから読んでも作業を継続できる**引き継ぎプロンプトに変換する。
要約レポートではなく「次のセッションへの指示書」を書くこと。

引数: `$ARGUMENTS`

## 出力形式の決定

引数の先頭トークンで出力先を決める。指定が無い場合は下記のルールで自分で選ぶ（選んだ理由を1行で述べる）。

| 引数 | 出力先 |
|---|---|
| `file` | Markdown ファイルに書き出す |
| `issue` | GitHub Issue を作成する |
| `inline` | チャットにそのまま出力する |
| 無指定 | 内容量で判断：短く（〜30行程度）まとまるなら `inline`、調査・設計・複数タスクを含み長くなるなら `file`。`issue` は明示指定のときだけ |

先頭トークンが上記以外なら、それも含めて全体を「引き継ぎたい焦点・補足」として扱う。

## 手順

1. **コンテキストを棚卸しする。** これまでの会話から次を拾う。会話の中に無い情報を推測で埋めないこと。
   - 元々のゴールと、その背景にある制約（納期・方針・触ってはいけない箇所など）
   - すでに確定した決定と、その理由。検討して**棄却した**選択肢とその理由も落とさない
   - 調べて分かった事実（ファイルパス・行番号・関数名・設定値・コマンド・エラーメッセージは原文どおり）
   - 実際に変更したファイルと、その変更内容
   - 未解決の論点、行き詰まっている点、ユーザーの判断を待っている点
   - 残タスク（優先順・依存関係つき）
2. **作業ディレクトリの状態を補う。** 必要なら `pwd` / `git status` / `git log --oneline -10` / `git diff --stat` を確認し、ブランチ名・未コミット変更・直近コミットを引き継ぎ先に伝える。git リポジトリでなければ省略。
3. **引数に焦点の指定があれば、そこを厚く書き、無関係な話題は削る。**
4. 下記テンプレートで本文を組み立てる。
5. 決めた出力先に応じて出力する（下記「出力先ごとの処理」）。
6. 最後に、次のセッションへ**そのまま貼れる1メッセージ**を提示する。ファイル／Issue の場合は本文を再掲せず、参照先を読ませる短い指示文にする。

## 引き継ぎ本文テンプレート

```markdown
# 引き継ぎ: <一行で分かるタイトル>

## ゴール
<何を達成したいのか。1〜3文>

## 前提・制約
- <方針、触ってはいけない箇所、環境の制約など>

## 作業環境
- 作業ディレクトリ: <絶対パス>
- ブランチ / 直近コミット: <git がある場合>
- 未コミットの変更: <あれば要約、無ければ「なし」>

## ここまでに分かったこと
- <事実。パスは `path/to/file.ts:42` の形式で>

## 決定事項
- <決めたこと> — 理由: <なぜ>
- 棄却: <選ばなかった案> — 理由: <なぜ>

## 変更済みのもの
- `path/to/file.ts` — <何をどう変えたか>
（変更がなければ「まだコード変更なし」と明記）

## 未解決 / 判断待ち
- <論点。ユーザーに確認すべきことはそう明記する>

## 次にやること
1. <具体的なアクション>
2. <...>

## 引き継ぎ先への注意
- <ハマりどころ、再実行してはいけないコマンド、既に試して失敗した方法など>
```

未確定の項目は空欄で残さず「未確定」「該当なし」と明記する。空セクションは削除してよい。

## 出力先ごとの処理

### file
- 保存先: 作業ディレクトリ直下の `.claude/handoff/<YYYYMMDD-HHmm>-<slug>.md`（`mkdir -p` してよい。日時は `date +%Y%m%d-%H%M` で取得）
- 書き込んだら**絶対パス**を提示する（相対パスだけでは別セッションの cwd が違うと開けない）
- 貼り付け用メッセージ例:
  ```
  /Users/.../.claude/handoff/20260812-1530-foo.md を読んで、そこに書かれた作業を続けてください。
  ```

### issue
- `gh auth status` と `gh repo view` でリポジトリと認証を確認する。使えない場合は `file` に切り替え、その旨を伝える
- **Issue の作成は外部への発信なので、タイトルと本文をチャットに提示してユーザーの承認を得てから `gh issue create` を実行する。** 承認前に作成しない
- 作成後は Issue の URL を完全な形で提示する
- 貼り付け用メッセージ例:
  ```
  <issue URL> を読んで、そこに書かれた作業を続けてください。
  ```

### inline
- 本文をそのままコードフェンスで囲んで出力し、ユーザーがコピーしやすい形にする
- 長くなりすぎる場合は途中で切らず、`file` に切り替えてその旨を伝える

## 守ること

- 会話に存在しない事実・ファイル・コマンドを創作しない。曖昧なところは「未確定」と書く
- パス・コマンド・エラー文は要約せず原文のまま残す
- 「頑張ってください」のような中身のない文を入れない
- ユーザーが承認していない方針を、決定事項として書かない
